## 0. Read this first

### 0.1 What we're building

A multipage personal portfolio for a software engineer targeting **all four résumé tracks: SWE/SDE/Founding Engineer, AI Engineer, general Forward-Deployed Engineer, and AI-specific Forward-Deployed Engineer** roles at US startups, mid-size companies, and MNCs.

Build an original portfolio and theme, using `Tukesh1/tukesh.in` only as inspiration. Do not assume its code, palette, or exact layout must be retained. Proceed phase by phase. The total hosting and service budget is $0; verify a viable deployment architecture before committing to providers.

### 0.2 Non-negotiables

1. **Original design.** Choose a cohesive, accessible theme with semantic tokens; upstream is inspiration only. Design decisions are delegated to the implementing agent.
2. **The owner must never edit a code or JSON file to update content.** Every piece of résumé-style content (experience, projects, skills, tools, certifications, socials, site metadata) is managed through an authenticated admin board. See §6 — this is the highest-value part of the build.
3. **Preserve specific technology names verbatim.** When pulling content from résumés, never abstract a concrete tool into a category. `Langfuse` must not become "observability tooling"; `QLoRA/PEFT` must not become "fine-tuning techniques"; a named vector DB must not become "cloud platforms." This is a deliberate ATS and credibility requirement.
4. **Attribution.** If upstream code/assets are reused, retain the applicable MIT license and attribution. Credit the design inspiration in the README.
5. **Publish explicitly.** All public content is editable through admin. Save creates a draft; only Publish changes the public site. Support authenticated previews and recoverable deletion.
6. **Phase checkpoints.** Consult §10 and `.preference/planning-questions.md` before each phase. Remind the owner about public résumé creation and project inputs at their respective checkpoints.

## 1. Phase 0 — Résumé ingestion (do this before any UI work)

**Goal:** turn four PDFs into one canonical, deduplicated, strongly-typed content seed.

### Steps

1. Extract text from each PDF in `resume/`. Note that the PDFs were generated by a react-pdf-based tool that has a **known ligature bug** — sequences like `fl` and `ffl` can extract corrupted (e.g. `workflows`, `offloads`). Sanity-check extracted text for mangled words and repair them; don't let corrupted tokens reach the database.
2. Build a comparison table (as a scratch artifact, not committed) of every **company, role, date range, and bullet** across all four variants.
3. Produce `seed/content-seed.json` — one canonical record per entity, merging the richest phrasing across variants. Where variants disagree on a metric, record it in `.preference/content-conflicts.md` rather than picking silently; keep seed JSON strictly valid.
4. **Ask the owner to confirm the merged record before seeding the database.** Do not invent metrics, dates, or scope that appear in no résumé.

## 2. Implementation direction

### Selected architecture

- **Frontend:** Next.js App Router, React, strict TypeScript, Tailwind CSS, Radix UI. React Hook Form and Zod provide form feedback.
- **Backend:** Python 3.12+, FastAPI, Pydantic v2, Uvicorn. FastAPI owns business rules, content validation, publishing, uploads, contact handling, and GitHub OAuth/session management.
- **Persistence:** SQLite locally, SQLAlchemy 2 ORM, Alembic migrations. Select durable production storage against the $0 constraint in Phase 1.
- **API contract:** versioned REST API under `/api/v1`; Pydantic/OpenAPI is authoritative, with TypeScript types generated for the frontend. Frontend validation supplements backend validation.
- **Authentication:** GitHub OAuth in Python using Authlib (for a maintained OAuth implementation), server-side sessions, HttpOnly/Secure/SameSite cookies, OAuth state validation, and CSRF/origin protection for cookie-authenticated mutations. Only Manishrdy is authorized. Prefer same-origin `/api` routing to simplify cookies and deployment.
- **Repository:** `backend/` for Python API, schemas, migrations, tests and CLI; `frontend/` for Next.js; `seed/` for the reviewable content draft. Neither frontend nor browser connects directly to SQLite.
- **Hosting:** Python-capable free hosting and durable database/media storage are not selected yet. The earlier Workers/D1 suggestion is not the selected deployment architecture. Verify the complete setup before committing to a provider.

### Preferred capabilities (verify compatibility and supported versions in Phase 1)
- Next.js App Router + React (supported patched versions) + TypeScript strict (no `any`).
- Tailwind (compatible version) + `@tailwindcss/typography`.
- MDX blog pipeline (`next-mdx-remote`, `gray-matter`).
- SEO stack: sitemap, OpenGraph, Twitter cards, JSON-LD (`Person`, `WebSite`, `ProfilePage`, `BlogPosting`), PWA manifest, RSS.
- `next-themes` dark/light with no flash.
- GitHub contribution calendar (dynamically imported, client-only).
- `lib/build-profile-text.ts` — the `llms.txt` / machine-readable profile builder. Use only approved published content; no private draft or source-PDF exposure.
- Performance budget: Lighthouse 95+, shared first-load JS under ~105 kB.

### Change
- The JSON-file data layer becomes a **database-backed layer** (§6). The `src/data/*.ts` thin adapters stay as the read interface — swap their internals from `import x from './json/x.json'` to a typed FastAPI request. Keep typed interfaces stable where practical; asynchronous rendering and new features may require component changes.

### Cut
- **Guestbook.** Low signal for a job-search portfolio and it carries moderation cost. Do not add it. Implement GitHub OAuth for admin (§6.3); inspect upstream wiring only if reusing code.
- **WakaTime integration.** Coding-hours stats read as vanity metrics to hiring managers and add an external dependency + API key. Keep the GitHub side of `/activity`; drop WakaTime.
- Upstream's Google Analytics ID (`G-P36W5PCJC2`) — remove or replace.

## 3. Original design system

Use upstream as inspiration, not a visual specification. The detailed interaction requirements below are starting points for our own implementation; claims about upstream internals are not verified requirements.

### 3.1 Color tokens

Choose an accessible dark/light palette and define semantic tokens for surface, raised surface, border, primary text, secondary text, and one accent. Use tokens throughout public and admin UI; keep raw color choices out of content data. No `iconColor` fields.

### 3.2 Typography

**Root cause:** Space Grotesk is loaded as `font-sans` and used for *everything* — headings, body copy, metadata, and code. It's a display-leaning geometric face; at 14–16px body sizes and in long MDX paragraphs it reads cramped and slightly wrong. That is exactly the "fonts look odd" symptom.

**Three font roles (agent-selected defaults):**

| Role | Family | Usage |
|---|---|---|
| Display | **Space Grotesk** | h1–h3, hero, nav wordmark, project titles |
| Body / UI | **Inter** | paragraphs, lists, metadata, form labels, admin board |
| Mono | **JetBrains Mono** | code blocks, inline code, dates in tabular contexts |

Implementation details:
- Load all via `next/font` with `display: 'swap'` and subset to `latin`. Expose as `--font-display`, `--font-sans`, `--font-mono`; wire into `tailwind.config.js` `fontFamily`.
- Define a **modular type scale** (1.25 ratio) as Tailwind size tokens rather than ad-hoc `text-[15px]`.
- Body line length: **max 72ch** for prose. Upstream's MDX column runs too wide on desktop.
- Headings: tighter tracking (`-0.02em`), body: default tracking.
- Enable `font-variant-numeric: tabular-nums` on dates, stats, and anything in a column.
- Do **not** accent a single word of a headline in a different color or weight.

### 3.3 Navbar

**Root cause:** upstream's header is a flat lowercase text list defined inline in `header.tsx`, with no active state, no mobile treatment, and no elevation — so it reads as unfinished chrome floating above content.

**Fix:**
- Sticky top, `backdrop-blur` with a semi-transparent `--surface`, hairline `--border` bottom that only appears once scrolled (`scrollY > 8`).
- **Animated active indicator** using Framer Motion `layoutId` — a single pill/underline that slides between items on route change. This is the one orchestrated motion moment on the page; keep motion elsewhere minimal.
- Sentence case labels, not lowercase-everything.
- **Mobile:** a proper slide-in sheet (Radix Dialog) triggered by a hamburger, not wrapped text. Trap focus, close on route change, close on Escape.
- Theme toggle lives in the nav, right-aligned, with an accessible label.
- Visible `:focus-visible` rings on every item.
- Respect `prefers-reduced-motion` — the indicator snaps instead of sliding.
- **Nav items come from the DB**, editable in the admin board (order + visibility), not hardcoded in `header.tsx`.

### 3.4 Floater / dock

**Root cause:** the floating panel has no defined z-index scale, no scroll behavior, and no mobile safe-area handling, so it collides with content and the footer.

**Fix:**
- Default: omit a redundant floating dock; keep primary actions in the navbar and page content. If usability review justifies a dock, use at most one and apply the following requirements.
- Define a z-index scale in the token layer (`--z-nav: 40; --z-float: 50; --z-modal: 60;`) and use only those.
- Hide on scroll-down, reveal on scroll-up, with a 150ms debounce.
- Honor `env(safe-area-inset-bottom)` on mobile; never overlap the footer — use an intersection observer to fade out when the footer enters the viewport.
- Hide entirely on `/admin` routes.
- Reduced-motion: no transform animation, just opacity.

### 3.5 Projects

**Root cause:** thumbnails mix local assets with GitHub's OG-image endpoint at different aspect ratios, descriptions are unbounded arrays, and tag lists have no overflow rule — so the grid never aligns.

**Fix:**
- Fixed **16:9** thumbnail via `next/image` with `fill` + `object-cover` + a blurred placeholder. Normalize *all* thumbnails to this ratio at ingest; if a project has no image, render a typographic fallback card (project initial + category), not a broken frame.
- Card height locked; description clamped to **2 lines** (`line-clamp-2`).
- Tags capped at **3 visible + "+N"**; full list on the detail page.
- **Category filter chips** (`web` · `ai-ml` · `agents` · `cli` · `data` · `open-source`) with state in the URL query so filters are shareable and back-button-safe. Include an "All" default and a real empty state with a next action.
- **Add `/projects/[slug]` detail pages.** This is a genuine gap: the owner has substantial systems work (full RAG pipeline, fine-tuning, a solo-built SaaS) that cannot be conveyed in a card. Detail page sections: problem → approach → architecture → stack → outcome/metrics → links. Content authored as MDX, managed from the admin board.
- Featured projects on the home page continue to derive from a `featured` boolean.

### 3.6 Posts / blog

**Root cause:** the post list is title + date only, and MDX prose styling is inconsistent across heading levels and code blocks.

**Fix:**
- Post list rows: title, one-line description, date, **reading time** (computed, not stored), and tags.
- Post detail: sticky table of contents on desktop (h2/h3), prev/next navigation, and a **copy button** on every code block.
- Normalize the `prose` scale against the new type system (§3.2) — heading sizes, code block padding, blockquote treatment, table borders all drawn from tokens.
- Per-post dynamic OG image via `@vercel/og`.
- Tag index at `/posts/tags/[tag]`.
- Rename the route from `/post` to `/posts` (plural), with a permanent redirect from the old path.

## 6. The admin board (highest priority after Phase 0)

### 6.1 Decision record

Custom authenticated `/admin` with SQLite preferred for local development. Use Python FastAPI, SQLAlchemy, Alembic, and authoritative Pydantic validation; Zod provides frontend form feedback. Production storage/hosting remains a Phase 1 decision: verify a durable free deployment, including database writes, media, backups, authentication, email, and analytics. Do not assume a local database file persists on an arbitrary host. Consider a SQLite-compatible hosted free option or another free database only after checking current terms and runtime compatibility. Do not provision paid plans or enable automatic paid upgrades.

### 6.2 Data model

The following are logical entities, adapted to the chosen database. Arrays require an explicit SQLite representation and validation.

```
site_settings   singleton — name, tagline, siteUrl, description, keywords[],
                socialBanner, resumeUrl, ogDefaults, hero, bio, contactCopy, footerCopy
education       id, institution, qualification, field, startDate, endDate, summary, order
page_content    id, route, section, content, order
social_links    id, label, href, icon, order, visible
nav_items       id, label, href, order, visible
experience      id, company, role, employmentType, location, startDate, endDate,
                current, summary, bullets[] (markdown), skills[], logo, order
projects        id, slug, title, category, tagline, description[], tags[],
                thumbnail, repoUrl, liveUrl, featured, startDate, endDate,
                projectStatus, bodyMdx, order
skills          id, group, name, level, icon, order
tools           id, name, icon, url, order
certifications  id, title, issuer, issuedOn, credentialUrl, badgeImage, order
posts           id, slug, title, description, bodyMdx, tags[], publishedAt,
                updatedAt, status(draft|published), ogImage
media           id, url, alt, width, height, blurDataUrl, mimeType, uploadedAt
revisions       id, entityType, entityId, payload, createdAt
publications    id, publishedSnapshot, publishedAt
```

Notes:
- Publishable entities have draft revisions and published revisions; editing a published item must not change its live version until Publish. Publication state is separate from project progress.
- Add visibility and deletedAt where applicable; deletion/reordering/visibility changes follow the same draft/publish workflow. Provide trash and restore; do not delete referenced media prematurely.
- Publish atomically creates a consistent public snapshot. Public pages, SEO, feeds, downloads, and llms.txt read only published content. Preview is admin-only and excluded from public caching/indexing.
- Every list table has an explicit integer `order` column — ordering is a content decision, not an accident of insertion.
- No `iconColor` anywhere (§3.1).
- `bullets[]` and `description[]` keep upstream's lightweight markdown support (`**bold**`, `[links](url)`).
- Preserve source date precision: résumé months use ISO YYYY-MM, exact known dates use YYYY-MM-DD. Never invent a day or silently choose conflicting dates; unresolved values remain null in the review draft.

### 6.3 Auth

- GitHub OAuth handled by the Python backend via Authlib; no separate Auth.js identity/session system.
- Single-admin allowlist via `ADMIN_GITHUB_USERNAME=Manishrdy`. Anyone else authenticating gets a 403, not a redirect loop.
- Protect `/admin/*` in the frontend and every `/api/v1/admin/*` endpoint with backend session authorization. Verify authorization on every mutation; frontend guards are not the security boundary.
- All business mutations go through FastAPI with Pydantic boundary validation. Next.js must not implement a second mutation/database layer.

### 6.4 Board UI

Routes: `/admin` (dashboard), `/admin/experience`, `/admin/projects`, `/admin/skills`, `/admin/tools`, `/admin/certifications`, `/admin/posts`, `/admin/settings`, `/admin/media`, `/admin/pages`, `/admin/education`, `/admin/navigation`, `/admin/socials`, `/admin/resume`, `/admin/trash`.

Requirements:
- Uses the same design tokens as the public site — the board should feel like part of the product, not a bolted-on CRUD screen.
- List view per entity: table with inline visibility toggle, **drag-to-reorder** (`dnd-kit`), duplicate, and recoverable delete-with-confirm.
- Edit view: a real form (`react-hook-form` + Zod form schemas aligned with the backend API contract), with markdown/MDX fields getting a split editor + live preview pane.
- **Unsaved-changes guard** on navigation.
- Optimistic updates with rollback on failure.
- Upload images and approved public PDFs to durable storage selected within the $0 budget; write media metadata and image blur placeholders. Validate upload type/size. Keep unpublished media access-controlled.
- Save persists a draft. Publish commits the approved revision and invalidates affected public routes using the selected runtime’s caching mechanism. Report publishing success only after it succeeds; preserve the previous published version on failure.
- All editable public content supports drafts, explicit Publish, and preview for the authenticated admin only.

### 6.5 Implementation and recovery

1. Build schema + migrations.
2. Write a Python seed CLI that ingests `seed/content-seed.json` (from Phase 0).
3. Implement typed data adapters; adapt components as needed for asynchronous reads and the original design.
4. If upstream JSON adapters are reused, remove them only after verifying content parity.
5. Keep backups private, including draft content and media; repository is private for now. Implement export/restore and verify a restore. Never commit full database dumps to public Git history.
6. Persist a separate last-published snapshot for outage fallback; test serving it with the database unavailable. An export script alone is not a fallback. Choose a private backup schedule/storage within the $0 budget during Phase 1.

## 11. Guardrails for the implementing agent

- Don't add libraries not named here without saying why. The performance budget is real.
- Don't introduce fade-and-slide-up entrances on every section, hover lifts on every card, or scattered scroll animations — one orchestrated motion moment (the nav indicator) is the budget.
- Don't add ALL-CAPS eyebrow labels above headings, middle-dot meta strings, or `→` glyphs appended to link text.
- Don't write placeholder copy and leave it. Every string ships as final copy drawn from real content.
- Don't let the admin board diverge visually from the public site.
- Ask before deleting anything from `resume/` or overwriting `content-seed.json`.
